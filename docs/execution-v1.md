# Isolated execution protocol v1

The pure ./execution entry defines RunRequest, output messages, terminal outcomes and a host-provider coordinator. The headless workspace ports never evaluate source code. Execution requires an explicit captured host policy execution=true and an approved provider. Remote sandbox providers additionally require captured network permission for the host transport (separate from the learner's always-disabled network). Missing drivers and denied permissions fail without invoking a factory. Input cannot select environment variables, credentials, command-line flags, host paths or mounts.

RunRequest executionVersion 1.0.0 binds an execution UUID to activity/session/optional attempt, generation and workspace revision. It declares a language and exact runtime ID/version, a normalized relative entrypoint and learner-only UTF-8 files. Project WorkspaceFile into {id,path,encoding,text}; do not copy editor metadata, credential fields or trusted hidden tests. Duplicate/case-colliding paths, ancestor-file conflicts, traversal, unsupported encodings and foreign fields are rejected.

Every request declares wallTimeMs, memoryBytes, outputBytes, workspaceBytes, processes and scratchBytes. The global ceilings are 30 seconds, 256 MiB, 256 KiB output, 1 MiB source, 64 processes and 1 MiB scratch. Filesystem is read-only-workspace with bounded isolated scratch; network is none. These are data requirements plus host-enforced limits, not promises that a JavaScript reducer can enforce an OS boundary.

Providers declare a captured manifest with exact runtimes and affirmative enforcement for time, memory, output, filesystem, network and processes. Eligible profiles are container and remote-sandbox. Hosts must approve/verify the implementation; a declaration alone is not a security proof. Browser Workers cannot provide a hard memory limit or an OS filesystem boundary and are not accepted as this isolation profile. A browser frontend can use the same request/message/terminal protocol through an approved remote sandbox service. No browser eval/Function/vm fallback is provided.

Output messages carry executionVersion, executionId, contiguous sequence, stdout/stderr channel and bounded text. The coordinator imposes its own encoded-text quota and ignores output after cancellation or context changes. Program output may contain learner-supplied sensitive text; it is local execution output, not automatically transmitted telemetry. Render as plain text and apply host privacy policy.

Terminal status is completed, failed, timed-out or cancelled, with a static reason, optional exit code and cleanupComplete. Completed requires exitCode=0 and acknowledged cleanup. This is an execution outcome, never a learner correctness score. Native provider exceptions and malformed outcomes become safe static failures, without host exception messages. Cleanup-incomplete outcomes are returned for host recovery and never trigger the committed terminal callback.

The coordinator deduplicates identical in-flight/retained execution IDs (at most 16 records) and rejects conflicting content. Retention is bounded, not durable exactly-once execution. A new run supersedes the previous operation and aborts its host signal. Messages and terminal callbacks additionally require exact identity/generation/revision; stale callbacks cannot update newer workspaces or restored/disposed sessions. Host callbacks are isolated. The provider owns all child processes/workers and must stop them before acknowledging cleanup. Noncooperative cancellation gets a bounded cleanup wait and reports cleanupComplete=false rather than claiming termination.

Core#3 may consume recorded terminal results as host-owned effect outputs; respect its tighter effect JSON budgets when choosing source/output quotas. This coordinator's public request budget is 2 MiB and does not implicitly weaken Core's 1 MiB effect budget. No in-flight execution, provider object or credentials belong in a snapshot. Core#4 generation rotation invalidates pre-restore runs. Durable remote submission authorization/idempotency and isolated trusted assessments are separate host responsibilities.

## Optional Linux Docker provider

The Node-only ./providers/docker entry is a trusted host adapter. It requires a locally present approved image digest and verifies the exact Node runtime version and Docker Linux memory/swap/process/CPU limit support. It never pulls an image or inherits host environment into a learner container. CI resolves an approved Node 22 image to a digest before testing it.

Each run gets a unique private container name and a freshly generated source directory. The container uses network=none, a read-only root filesystem, read-only learner workspace, unprivileged numeric user, no Linux capabilities, no-new-privileges, private PID namespace, bounded tmpfs scratch, cgroup memory/swap and process limits, and a wall-clock kill deadline. Only the generated learner directory is mounted. No Docker socket, host home, credential files or environment secrets are passed.

The interpreter/entrypoint flags are fixed by the trusted adapter; learner requests cannot override them. Container logs are buffered under quota and delivered only after successful log retrieval and acknowledged container/source cleanup. Docker client/daemon stderr is discarded and replaced by static codes, preventing native host paths/errors from entering learner logs. Stream bytes are decoded as UTF-8 with replacement for malformed output; the coordinator separately counts the encoded resulting text.

Cancellation/deadline/output overflow forcibly removes the entire container, including children, and discards delayed buffered output. CleanupComplete requires an actual Docker absence response for the private container and successful removal of the generated source directory. A disconnected/unresponsive daemon cannot be interpreted as successful cleanup.

This provider shares the host kernel, unlike a VM or stronger sandbox runtime; its guarantees are the verified container controls above. It is not a kernel-breakout defense or an implicit multitenant deployment service. The trusted host owns Docker access, image approval, daemon lifecycle and resource-recovery operations. Remote providers must document and test their own corresponding controls before registration.

CI uses real containers for stdout/stderr, host environment/file isolation, workspace/root write denial, network denial, infinite code deadlines, excessive output, cancellation with a spawned child and absence of leftover containers. Pure tests cover structural permission gates, unsupported browser profiles, identity/revision staleness, bounded messages, retained duplicate behavior and incomplete cleanup.
