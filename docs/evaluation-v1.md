# Code evaluation v1

Running code produces execution outcomes, not a grade. Optional evaluation entry points do not alter CodeConfig, workspace snapshots or Protocol wire schemas. A Submission owns a frozen v1 RunRequest and a SHA-256 protocol-canonical JSON digest of language, runtime, entrypoint and files. Submission UUID, activity/session/attempt, generation and revision bind its evaluation. A host must derive getCurrent from trusted runtime state; requests and response fields are untrusted.

The learner entry evaluation contains submission and remote orchestration only. The separate evaluation/trusted entry and its test suite belong on the trusted server (or explicitly non-secure local practice host). Never import it or private tests into a learner/browser bundle. Public practice tests are a separate TestSuite v1: case id, input string, exact expected stdout string and nonnegative weight. Private suites have the same internal shape but are never projected into learner specs, snapshots, events, records or request payloads. Inputs/expected outputs never appear in reports, even for public suites. Public feedback exposes only case id, static status and binary credit. Secure reports contain no case details.

A trusted runCase closure owns compiler selection, isolated provider calls, stdin provisioning and test execution. This library supplies no stdin-enabled Docker adapter, compiler driver or assessment server. Code#2's provider runs source; it must not be treated as a test or an evaluator. Trusted tests/assertions cannot run in the learner process and establish authority. Hosts must enforce Code#2 resource/network/filesystem/process limits for every test and authenticate assessment responses. Remote identity checks are correlation, not authentication.

Completed execution stdout is compared byte-for-byte as a JS Unicode string, with no trimming, newline or Unicode normalization. Passed cases earn 1, assertion failures 0; weighted sum / total weight yields [0,1]. Zero-weight cases remain diagnostic; total weight must be positive. Compile/runtime errors yield a zero-score completed result and a distinct category. Infrastructure errors produce failed Protocol results with no score. Pending evaluation produces pending with no score. Infrastructure retries (0..3) replace that case's outcome; no outcome contributes twice. Case order and aggregation order follow declarations. Async trusted callers must supply host deadlines/signals; the remote client enforces its own bounded deadline, consumes late promise failures and excludes stale responses.

The remote client copies inputs before awaiting, recomputes digest, deduplicates identical in-flight and retained terminal submissions, rejects ID conflicts, and tracks at most 64 verification admissions plus 16 retained results by default. A new admitted submission supersedes prior verification/evaluation. Restored generation, new attempt or changed file revision prevents application. Terminal records contain aggregate reports only; no files/test material. Timeout/cancellation are safe failed results. Failed transport/malformed responses are infrastructure failures. Response evidence, raw stdout, raw failure messages and private feedback are discarded. Protocol result validators are trusted synchronous ports. Polling a pending submission explicitly calls evaluate again under the same id; pending responses are not cached as terminal. Exactly-once grading across process restarts, server retries and evicted IDs requires host durable idempotency.

No automatic Core state mutation, telemetry emission, snapshot persistence, package release or browser integration is added. Hosts apply a non-ignored result once via the relevant action/effect contract and preserve the immutable submission binding. Changing these optional contracts requires explicit versioning; v1 shared contracts remain unchanged.
